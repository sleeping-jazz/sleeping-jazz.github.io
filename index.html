# SOS Emergency Alert App

final stack = ['Flutter', 'Dart', 'Geolocation API',
'SharedPreferences', 'Android SMS'];

## What it does

One tap fetches the phone's live GPS position and texts it, as a Google Maps link, to up to three saved contacts and a helpline number. It needs no internet connection and no account: it uses only the device's GPS and the native SMS service.

## Highlights

  • Contacts and the helpline number are stored on the device with SharedPreferences, so there is no backend to run.
  • On dual-SIM phones the alert goes out through every active SIM, which improves the odds that it gets delivered.
  • Handles runtime permissions for SMS, phone and location, including the case where the user denies them.
  • Tested end to end on a physical Android device and built as a release APK.

## Challenges

  • Android emulators don't run on my ARM-based laptop, so all development and debugging happened on a physical phone.
  • Flutter and Dart were both new to me, so the first stretch was a steep learning curve.
  • Deciding how to fall back between SIMs when one has no balance or a weak signal while the other works.

# Gmail AI Draft Assistant

stack = ["Python", "Gmail API", "OAuth 2.0",
"Ollama (Llama 3.2:3B)", "SQLite"]

## What it does

Reads unread Gmail messages, decides which ones need a reply, and saves a draft written by a language model running locally through Ollama. It never sends mail itself: you read each generated reply and confirm it before it is saved as a Gmail draft.

## Highlights

  • Google OAuth 2.0 sign-in with a reusable local token.
  • A SQLite table records every processed message, so an email is never classified or drafted twice across runs.
  • Llama 3.2:3B runs locally via Ollama: no paid AI API, and email text isn't sent to a third-party AI service.
  • Split into separate modules for authentication, email retrieval, AI classification and drafting, the database, and draft creation.

## Challenges

  • The cryptography package failed to build while installing the Google auth libraries. Moving to Python 3.12, which has pre-built wheels for it, fixed that.
  • For tracking processed mail I weighed simply marking emails as read against a SQLite table, and chose the database for more reliable, detailed tracking.
  • The small local model sometimes misjudges whether a reply is needed. Occasionally, after you confirm, it copies the original email into the draft instead of writing a reply. This is a known limitation.
  • Google Cloud Console (the OAuth consent screen and credentials) was new to me and took time to learn.
  • Only plain-text emails are handled so far. HTML email support is planned.

# Digital Music Player

const std::vector<std::string> stack =
{"C++17", "Windows MCI API", "winmm"};

## What it does

A console music player in C++ that plays real MP3 and WAV files through the Windows MCI API. The playlist is a circular doubly linked list that I wrote myself, so next and previous wrap around without any boundary checks.

## Highlights

  • Inserting, deleting and moving to the next or previous track are all O(1), using a cursor into the list.
  • Import a single file or a whole folder, then shuffle (O(n), since every node is touched) or repeat the current track.
  • Three separate parts: the Playlist class holds the data structure, the Player class wraps MCI playback, and MusicPlayer.cpp is the console UI that connects them.

## Challenges

  • Importing more than one file at a time broke next-song navigation, which meant debugging the playlist's insertion and cursor logic.
  • Detecting when a track has finished, so the next one starts on its own, was hard to make reliable.
  • Folder import: scanning subfolders adds overhead, while importing only the chosen folder is simpler but repetitive for nested libraries. I chose the simpler, non-recursive version.
  • Known limitations: file names in non-English scripts (for example Hindi or Hawaiian) don't import correctly yet, it runs on Windows only because it uses MCI, and playlists aren't saved between sessions.
